# گزارش جامع تحلیل و رفع ریشه‌ای مشکلات مایگریشن‌های تسک‌یار ۲.۰
# TaskYar Web 2.0 — Critical Migration Repair & Technical Analysis Report

این گزارش فنی، مستندسازی جامع علل بروز خطاهای مایگریشن در محیط پروداکشن دایرکت‌ادمین (DirectAdmin)، تحلیل ریاضی طول کلیدهای ایندکس تحت یونیکد `utf8mb4`، و راهکارهای مهندسی پیاده‌سازی‌شده برای تضمین سازگاری ۱۰۰٪ با انواع موتورهای ذخیره‌سازی MySQL و MariaDB را تشریح می‌کند.

---

## ۱. کالبدشکافی ریشه‌ای خطاهای پروداکشن (Root Cause Analysis)

### ۱.۱. خطای اول (Failure A) — فراتر رفتن طول کلید از سقف مجاز (MySQL Error 1071)
**پیام خطا:**
```text
SQLSTATE[42000]: Syntax error or access violation: 1071
Specified key was too long; max key length is 1000 bytes
SQL: create table `password_reset_tokens` (`email` varchar(255) not null, ...)
```

**تحلیل فنی و محاسبات بایت:**
1. در سیستم استاندارد انکودینگ لاراول از مجموعه نویسه `utf8mb4` (با تطبیق `utf8mb4_unicode_ci`) استفاده می‌شود تا کاراکترهای ۴ بایتی، ایموجی‌ها و نویسه‌های گسترده فارسی به درستی پشتیبانی شوند.
2. هر کاراکتر در `utf8mb4` حداکثر **۴ بایت** فضا در ایندکس اشغال می‌کند.
3. ستون پیش‌فرض ایمیل به صورت `VARCHAR(255)` تعریف شده بود. محاسبه اندازه بایت کلید:
   $$255 \times 4 = 1020 \text{ bytes}$$
4. در سرورهای هاست اشتراکی DirectAdmin، بسته به تنظیمات پیش‌فرض سرور، فرمت ردیف جدول (`Row Format`) و نوع موتور (مانند موتور MyISAM با سقف سخت ۱۰۰۰ بایت، یا فرمت COMPACT/REDUNDANT در موتور InnoDB با سقف ۷۶۷ بایت)، سقف کلید ایندکس معادل **۱۰۰۰ بایت** است.
5. از آنجا که ۱۰۲۰ بایت بزرگتر از ۱۰۰۰ بایت است ($1020 > 1000$)، مای‌اس‌کیوال دستور ایجاد جدول را با خطای ساختاری `1071 Specified key was too long` متوقف کرد.

### ۱.۲. خطای دوم (Failure B) — مایگریشن ناقص و خطای تکراری بودن جدول (MySQL Error 1050)
**پیام خطا:**
```text
SQLSTATE[42S01]: Base table or view already exists: 1050
Table 'users' already exists
Migration: 0001_01_01_000000_create_users_table
```

**تحلیل فنی عدم پشتیبانی DDL از تراکنش‌ها در MySQL/MariaDB:**
1. در سیستم‌های پایگاه داده رابطه‌ای مبتنی بر MySQL و MariaDB، دستورات تعریف ساختار داده یا **DDL** (نظیر `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE`) مشمول **Implicit Commit** (تأیید ضمنی) می‌شوند و نمی‌توان آن‌ها را درون یک تراکنش اتمیک (`BEGIN TRANSACTION ... ROLLBACK`) برگشت داد.
2. فایل اولیه `0001_01_01_000000_create_users_table.php` حاوی سه دستور مجزای ساخت جدول بود:
   - ساخت جدول `users` (با موفقیت در دیتابیس ثبت و تثبیت شد).
   - ساخت جدول `password_reset_tokens` (با خطای ۱۰۷۱ متوقف شد).
   - ساخت جدول `sessions` (اصلاً اجرا نشد).
3. فریم‌ورک لاراول تنها در صورتی نام یک فایل مایگریشن را در جدول ردیابی `migrations` درج می‌کند که کل متد `up()` آن بدون خطا پایان یابد. به دلیل بروز استثنا در خط ساخت جدول توکن‌ها، ثبت این مایگریشن در جدول `migrations` ثبت نشد.
4. هنگامی که مدیر سرور خطا را اصلاح کرد و مجدداً `php artisan migrate` را زد، لاراول متد `up()` را از ابتدا اجرا کرد و تلاش نمود مجدداً جدول `users` را بسازد که بلافاصله با خطای `1050 Table 'users' already exists` متوقف شد.

### ۱.۳. خطای سوم (Failure C) — خطای شبکه و اتصال سوکت به جای TCP
**پیام خطا:**
```text
SQLSTATE[HY000] [2002] Establishing tcp connections on remote port 3306 has been disabled for security reasons. Host: 127.0.0.1
```
**علت و حل نهایی:**
روی هاست‌های اشتراکی با فایروال‌های سخت‌گیرانه، ارتباط TCP لوکال روی پورت ۳۳۰۶ برای آدرس `127.0.0.1` بسته است. با تغییر مقدار به `DB_HOST=localhost`، کتابخانه کلاینت دیتابیس از سوکت محلی یونیکس (`/var/lib/mysql/mysql.sock` یا مشابه آن) استفاده می‌کند که صد در صد پایدار و ایمن است.

## ۳. تغییرات پیکربندی سراسری فریم‌ورک

### ۳.۱. تنظیم سقف طول رشته در `AppServiceProvider`
در فایل `app/Providers/AppServiceProvider.php` خط زیر در متد `boot` افزوده شد:
```php
public function boot(): void
{
    Schema::defaultStringLength(191);
}
```
این تنظیم استاندارد رسمی لاراول تضمین می‌کند حتی اگر پکیج جانبی یا توسعه‌دهنده‌ای در آینده از `$table->string('name')` بدون تعیین طول استفاده کند، طول ستون روی ۱۹۱ کاراکتر (۷۶۴ بایت) محدود شود و هرگز هیچ خطای ۱۰۷۱ در سرور رخ ندهد.

### ۳.۲. اجبار صریح موتور InnoDB در `config/database.php`
در تنظیمات کانکشن‌های `mysql` و `mariadb`:
```php
'engine' => env('DB_ENGINE', 'InnoDB'),
```
این کار تضمین می‌کند که حتی اگر پیش‌فرض سرور هاستینگ روی MyISAM یا Aria تنظیم شده باشد، تمام جداول با موتور استاندارد و تراکنشی **InnoDB** ایجاد شوند.

## ۴. معرفی دستور اختصاصی عیب‌یابی: `taskyar:diagnose`

برای راحتی مدیران سرور و عیب‌یابی سریع سناریوهای مختلف بدون ریسک تخریب داده‌ها، دستور رسمی زیر طراحی و به پروژه اضافه شد:
```bash
/usr/local/php-8.4/bin/php artisan taskyar:diagnose
```
این دستور:
1. وضعیت اتصال دیتابیس و نسخه نرم‌افزار سرور را ارزیابی می‌کند.
2. وضعیت وجود تک‌تک ۱۴ جدول اصلی برنامه را گزارش می‌دهد.
3. تعداد رکوردهای کاربران و تسک‌ها را می‌شمارد تا وجود داده‌های واقعی را تأیید کند.
4. سناریوی دقیق محیط را مشخص می‌کند (سناریوی A: نصب تازه، سناریوی B: نصب ناقص بدون دیتا، سناریوی C: پروداکشن فعال با دیتا، سناریوی D: ناهمگونی تاریخچه).
5. دستور دقیق و امن بازیابی را به کاربر پیشنهاد می‌دهد.
